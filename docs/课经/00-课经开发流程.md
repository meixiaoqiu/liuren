# 课经开发流程

本文规定六十四课及其下属格的统一开发流程。目的不是让智能体凭对话记忆继续工作，而是把“古籍原文如何转成可执行规则”的调查、决策、实现和验收过程固化为仓库规范。

本流程适用于新增课、格，或修改既有课格的成立条件、课义判断、课例与前台推理信息。

## 一、基本原则

1. **先研究规则，再编写代码。** 不得先写一个能命中课例的条件，再倒推古文为它背书。
2. **原文、解释、程序条件必须分开。** 原文引用不得混入白话补充；程序采用的解释不得冒充古籍原句。
3. **不同文献、不同段落、不同课例不得拼接。** 《六壬大全》正文、《观月经》《心镜》《订讹》等材料须分别标明出处；即使同列在一课之下，也不能默认属于同一课例。
4. **不自创六壬概念或输入条件。** 古籍没有给出的“命五行”、状态、权重、格名等，不得为了让算法闭合而新增。
5. **一课可以与其他课重合。** 课格系统是条件过滤系统，不得仅因一盘已命中另一课，就排除当前课。
6. **测试只证明代码符合已写断言，不证明古籍解释正确。** 解释正确性必须由原文、旁证、课例和枚举共同论证。
7. **没有覆盖的内容必须明确记录。** 不得用放宽条件代替尚未实现的条件，也不得让前台产生已经判断的错觉。

## 二、资料收集与校勘

开发开始时，先建立该课独立笔记 `docs/课经/NN-课名课.md`，至少收集以下内容：

- 《六壬大全》课经正文、象曰及全部课例；
- 正文同页所附《观月经》等材料，但须单独标注来源；
- 可取得的《心镜》《订讹》《袖中金》《六壬粹言》等旁证；
- 不同版本的异文、断句差异和现代白话解释；
- 每条材料的可核验链接、书名、卷次或影印页信息。

资料优先级原则上为：

1. 可核验的《六壬大全》原文或影印本；
2. 与《大全》时代相近或被其引用的古籍材料；
3. 其他传统六壬文献的明确规则与课例；
4. 现代整理、白话解读与网站结果，仅作线索或交叉验证，不单独决定规则。

现代资料与古籍冲突时，应记录冲突，不得静默覆盖古籍。图解、白话本存在删节或误释的可能，引用时须与正文核对。

## 三、原文语义拆解

在编码前，必须逐句拆解成逻辑候选。重点检查：

- “凡”“或”“及”“并”“更”“但”“若”等连接词表示 `AND`、`OR`、递进、增强还是例外；
- “发用”“入传”“传中”“初传”“中传”是否被混用；
- “临”“加”“乘”“坐”“上见”分别指地盘宫位、天盘上神还是所乘天将；
- 条件是成课必要条件、格的分支条件、增强条件，还是象义修证；
- 多个条件是否必须落在同一神、同一传位或同一对象上；
- 原文课例给出的是通用定义，还是只用于说明某一种特殊结构。

笔记必须用下表记录，不得只写最终结论：

| 原文 | 候选解释 | 精确逻辑 | 支持证据 | 反对证据 | 影响范围 |
| --- | --- | --- | --- | --- | --- |
| 原句逐字引用 | A / B / C | 可转为代码的与或关系 | 课例、旁证、语法 | 反例、异文、不可达性 | 各候选命中数量 |

若原文存在歧义，必须回答：

1. 能否在《大全》其他章节找到相同句式的用例？
2. 全部正文课例分别支持哪些候选？
3. 其他古籍是否给出第二课例或更明确的定义？
4. 候选规则在真实排盘中是否可达？
5. 不同候选在 720 核心盘或指定年份中是否实际等价？
6. 哪个候选最符合语法、课例、旁证和合理命中规模？
7. 最终倾向哪个解释，置信边界是什么？

不能消除歧义时，可以采用“现阶段最合理解释”，但必须在笔记中保留其他候选、选择理由和重新评估条件，不得写成“原文已经毫无歧义”。

## 四、课例反推与可达性验证

每个《大全》正文课例都必须单独复原，不得只验证其中最容易的一例。

复原时依次核对：

1. 日干支、占时、月将；
2. 天地盘关系与四课；
3. 三传及取传方式；
4. 昼夜贵、顺逆布将和三传所乘天将；
5. 月份、季节、太岁、月建等时间条件；
6. 本命、行年、性别、配偶等人物上下文；
7. 原文点名的每一项结构是否真实出现。

古籍未给现代年月日时，只给“某日、某时、某将”时，应在足够大的年份范围搜索真实可执行时间。不得手工拼装一个生产排盘程序永远无法生成的对象充当标准案例。

古籍没有提供出生资料，而规则又必须依赖年命时，可以补充一组现代出生资料来复现盘面，但必须明确标注“现代补充资料”，不得说成古籍原例所载。

发现课例无法复原时，应优先排查：

- 是否混入了另一段文献的年龄、月份或人物条件；
- 月将、昼夜贵、换日、立春或日出日落口径是否不同；
- 是否存在传抄、断句或现代解读错误；
- 当前排盘核心是否可能有错误。

不得仅因暂时无法复原就宣布古籍错误，也不得为迁就孤例静默修改核心排盘。

## 五、候选规则枚举与命中率

确定候选规则后，必须做可重复的枚举，而不是凭“看起来太多／太少”判断。

至少提供：

- 720 核心盘中的命中集合或数量（适用于不依赖动态时间和人物上下文的规则）；
- 一个完整公历年的命中数量，通常按每天十二个代表时辰统计；
- 若规则依赖昼夜贵、节气或真实年月，须使用真实时间扫描；
- 若规则依赖本命、行年、性别或配偶，须固定并公开出生资料，同时分别统计必要的上下文组合；
- 多个候选规则的交集、差集和包含关系；
- 命中率分母、时区、年份、采样时刻及所有人物资料。

统计脚本应放在 `tests/Support/Statistics/`，只读调用生产排盘与规则代码，能够在 Docker 容器中重复执行。笔记不得引用不存在的脚本，也不得保留无法复现的旧数字。临时探查脚本完成后应删除。

命中很多或很少都不是单独否决理由，但必须用于检查：

- 条件是否被错误解释成任一满足；
- 本应落在同一对象上的条件是否被拆散；
- “并”“及”等限制是否被忽略；
- 规则是否收紧到正文课例都不能命中；
- 该课是否已经失去区分意义。

## 六、最终规则决策

编码前必须给出一段无歧义、能直接翻译为程序的自然语言规则，并同时给出布尔公式。例如：

```text
德庆课成立：
初传属于四德之一
AND 初传乘六吉将之一
AND（初传加临本命宫 OR 初传加临行年宫）
```

最终决策说明至少包含：

- 采用的规则；
- 未采用的候选规则；
- 选择依据；
- 《大全》全部正文课例是否命中；
- 候选规则命中数量对比；
- 尚存歧义和未来推翻当前结论所需的证据。

如课下存在格，应分别建立课级规则与格级规则。课、格定义不得混写；同一课可以无格，也可以命中多个格，具体依原文而定。

## 七、代码实现要求

每一课开发通常应同步检查或修改：

- `app/Domain/Pan/Rules/*Rule.php`：课或格的判断；
- `app/Domain/Pan/Rules/RuleRegistry.php`：规则注册；
- 必要时建立共享 Support，但不得把当前课的偶然结构扩散成全局概念；
- `resources/views/livewire/pan/partials/*-trace.blade.php`：可核对的推理过程；
- `resources/views/livewire/pan/create-pan.blade.php`：引入对应 trace；
- `app/Support/KeJingCatalog.php`：课名、卦名、卦符、摘要与课例；
- `tests/Unit/*RuleTest.php`：独立规则边界；
- `tests/Feature/FrontendPanTest.php`：前台展示；
- `tests/Feature/KeJingPageTest.php`：目录和课例可执行性；
- `docs/课经/NN-课名课.md`：完整研究记录。

每个新增 PHP 文件顶部应有中文注释，说明文件作用、规则边界和重要口径。规则命名应优先使用准确拼音或项目既有术语，不得自行创造容易误导的英文译名。

前台推理应展示真实盘面证据，例如“初传巳乘太阴”“地盘子位上神为巳”，而不是只显示“条件成立”。客观盘面、规则判断、未覆盖项须区分展示。

## 八、`/kejing` 课经页面要求

每一课至少提供一条真实可执行案例；《大全》正文有多个体现不同规则路径的课例时，应尽量全部收入。

案例字段至少包括：

- 稳定且语义化的 `case_id`；
- `label` 与选择理由 `reason`；
- 起课时间；
- 必要的出生时间、性别、配偶等上下文；
- `status`。

状态只有：

- `executable`：点击后必须由正式规则真实命中所属课；
- `reference_only`：仅用于原文盘面参考，尚不能由正式规则命中。必须明确显示“原文参考盘·尚未覆盖”，不得伪装为完成案例。

新增或修改案例后，必须确认：

1. 链接参数能够复现相同盘面；
2. `executable` 案例进入排盘页后显示正确的课与格；
3. 推理区展示对应条件及具体证据；
4. 修改时间或人物资料后不会错误保留参考案例状态；
5. 课经摘要与实际规则一致；
6. 卦名、卦符、课、格层级和前台排序正确。

## 九、测试与回归

规则单元测试至少覆盖：

- 每个成立入口的正例；
- 每个必要条件单独缺失的反例；
- `AND` 两侧分别不成立的情况；
- `OR` 各分支分别成立的情况；
- 同一对象约束，防止多个无关位置拼成一次命中；
- 缺少人物上下文时返回 `not_evaluated`，而不是错误地判为不成立；
- 原文标准课例；
- 所有固定映射表的逐项校验；
- evidence 中的具体神、传位、天将与路径。

测试不得使用待测生产方法生成自己的预期值，也不得用“至少命中一次”冒充“列出的所有课例全部命中”。数据集测试必须逐条执行规则并逐条断言。

常规验收命令必须在 `php85-fpm` 容器的 `/var/www/html/liuren` 中执行：

```bash
docker exec -w /var/www/html/liuren php85-fpm php artisan test --filter 规则名
docker exec -w /var/www/html/liuren php85-fpm php artisan test tests/Feature/KeJingPageTest.php
docker exec -w /var/www/html/liuren php85-fpm php artisan test tests/Feature/FrontendPanTest.php
docker exec -w /var/www/html/liuren php85-fpm vendor/bin/pint --test
```

如果修改了核心排盘或天将逻辑，必须另按根目录 `AGENTS.md` 执行修改前后的 720 核心回归、独立天将测试、完整套件和基线审批流程。新增课格规则通常不修改 720 核心盘，但最终提交前仍应运行完整测试套件。

## 十、完成标准

只有同时满足以下条件，才能宣布该课开发完成：

- 《大全》正文、象曰和全部课例已经收集并准确分源；
- 重要语义歧义已经列全，并完成古籍旁证、逻辑分析和可达性检查；
- 已明确选择一个精确规则，未把倾向写成古籍定论；
- 《大全》正文课例已逐条复原，不能复原的已说明原因与状态；
- 候选规则命中数量已经用可重复脚本统计；
- 课、格、卦名和卦符层级正确；
- `/kejing` 摘要、案例链接与状态已同步；
- 前台展示了可核对的推理证据；
- 单元、前台、课经页面和必要回归测试通过；
- 未覆盖的象义、修证和异说已写入笔记；
- 工作区变更已完整报告，且未在未经授权时暂存、提交或推送。

若核心成立条件仍无法确定，只能标记为“研究中”或把具体案例设为 `reference_only`，不得宣布完成。

## 十一、每次交付的固定报告模板

后续智能体完成一课时，应按以下顺序报告，避免用户重复追问：

1. **最终精确规则**：自然语言 + 布尔公式；
2. **原文依据**：逐句对应，不混入解释；
3. **歧义与决策**：候选、旁证、反例、倾向和剩余边界；
4. **全部正文课例**：每例复原状态及具体盘面证据；
5. **命中统计**：分母、上下文、各候选数量与复现命令；
6. **代码实现**：课、格、Support、注册与 evidence；
7. **前台与 `/kejing`**：摘要、卦象、案例、状态和推理展示；
8. **未覆盖项**：只记录真实尚未实现内容；
9. **测试结果**：规则、课经页、前台、720、天将、完整套件、Pint 分开报告；
10. **工作区状态**：全部修改文件，明确是否暂存、提交、推送；
11. **完成结论**：明确写“完成”“现阶段完成”或“尚未完成”，并说明唯一剩余阻碍。

在这份报告完整之前，不应让用户再逐项追问“有没有歧义”“一年命中多少”“课经页面是否同步”或“是否可以结束”。
